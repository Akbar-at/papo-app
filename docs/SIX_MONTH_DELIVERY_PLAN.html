A delivery plan for the Windows Photo App, the Config App, and the services that connect them.

Based on the initial feature and ownership lists. Months are relative to project kickoff; no calendar start date has been assumed.

Starting point. The papo-app scaffold includes an application-managed authentication flow, admin provisioning screens, a session API, contracts and local tests. These are foundations to extend and validate, rather than proof of a production release. Camera/printer integration and the full feature list remain delivery work.

Identity decision. PAPO manages admin authentication and authorization within the application. Cloudflare Access is not a dependency.

Delivery sequence

Monthly milestones

Priority 1 journeys should be usable by the end of Month 3. Priority 2 operational features follow in Month 4, with Priorities 3–4 in Month 5. Testing runs throughout.

Month 01

Design and foundations

Photo App

Design the booth capture flow and UI. Confirm camera model, SDK, printer, paper sizes and Windows drivers. Prototype camera capture and physical printing.

Config App

Design navigation, sales dashboard, control panel, gallery and template editor. Define superadmin, operator and viewer access.

Services & infrastructure

Finalize architecture, database structure, hosting, private object storage, migrations, logging and application-managed authentication. Define device identity, sync contracts and traffic routing.

Exit gate: Approved core designs, agreed hardware choices, and a working camera-to-printer prototype.

Month 02

Capture and configuration

Photo App

Implement photo sessions, camera controls, capture timers, retakes, frame rendering, GIF generation and printing. Start durable local outbox and configuration sync.

Config App

Build the template editor, frame selector, booth/template assignments, price changes and camera settings. Add viewer accounts restricted to selected booths.

Services & infrastructure

Implement session/configuration services, versioned frame assets, device authentication, verified uploads and configuration acknowledgements.

Exit gate: One real booth captures, composes and prints using settings published from the Config App.

Month 03

Complete Priority 1 journeys

Photo App

Complete upload/finalization, private sharing links and QR delivery. Recover interrupted uploads and sync every implemented function.

Config App

Deliver sales dashboard, transaction list, booth-filtered gallery and sharing through link, email and QR. Complete and refine Priority 1 screens, including the template editor.

Services & infrastructure

Add background jobs, email delivery, image optimization variants, gallery permissions, retention and rate limiting. If paid sessions are included, integrate the selected payment sandbox and validated transaction flow.

Exit gate: A complete session reaches print, gallery, sharing and transaction reporting. Payment readiness depends on the agreed payment scope.

Month 04

Daily operations and Priority 2

Photo App

Add maintenance mode, print diagnostics/logs, reliable sync retries and clear recovery for camera/printer failures. Finish operational timer control.

Config App

Deliver maintenance screen, printing logs, timer controls, statistics and popular-frame reporting across selected booths. Add discount vouchers with expiry/booth restrictions and reusable vouchers.

Services & infrastructure

Implement agreed voucher eligibility/redemption rules, reporting aggregation, audit events, monitoring and database performance improvements.

Exit gate: Operators can manage routine work, investigate failures and reconcile voucher/transaction records.

Month 05

Fleet control and Priorities 3–4

Photo App

Add connected-computer status and controlled restart commands. Verify command acknowledgements, reconnect behavior and persistent outbox recovery.

Config App

Deliver connected-computer list, restart trigger and template groups. Add public galleries selected by booths, date range and time range, with sharing links.

Services & infrastructure

Harden remote-command authorization and gallery privacy. Run bounded 3 → 30 → 100 → 300 booth capacity stages, subject to test authorization. Tune database, queues, storage and traffic distribution using measurements.

Exit gate: Feature-complete pilot candidate, with capacity findings and unresolved release issues documented.

Month 06

Pilot, rollout and hypercare

Photo App

Pilot on real booth hardware. Resolve capture, printing, connectivity, local outbox and recovery defects.

Config App

Complete business acceptance testing, usability fixes, operator documentation and training.

Services & infrastructure

Validate security, backup/restore, recovery, monitoring and release procedures. Reserve the first half for pilot/fixes and the second half for staged rollout and hypercare, subject to acceptance.

Exit gate: Accepted pilot, controlled release and support handover. Extend hypercare if rollout or incident resolution needs more time.

Accountability

Ownership and coordination

Existing named ownership is preserved. Unassigned work needs a named person before kickoff; role labels below are proposed responsibility groups.

Arta Assigned

Camera/printer integration, Photo App frame mechanism, sync mechanism, sales dashboard, control panel and hypercare. Stagger dashboard/control-panel delivery alongside hardware work rather than assuming simultaneous full-time delivery.

UI / product To assign

Photo App UI, Config App UI and photobooth flow design. Coordinate template editor, gallery and operator usability with Arta and backend development.

Backend / infrastructure To assign

Architecture, database structure/infrastructure, object storage, backend services, each Photo App function's sync integration, authentication, queues, image variants, hosting, rate limiting and traffic routing.

Testing and acceptance Shared

Developers own automated/integration checks; the acceptance owner verifies real hardware and business flows. Assign a coordinator for release acceptance and support handover. Arta leads hypercare.

Dependencies and planning assumptions

  • Parallel staffing: the six-month target assumes UI and backend support alongside Arta. With Arta as the only implementer, reduce scope or extend the schedule.
  • Hardware gate: confirm camera/printer compatibility in Month 1. Integration and physical print quality must be accepted on the actual devices.
  • Template scope: agree editor capabilities, supported layouts, artwork formats and rendering/export behavior in Month 1; complexity directly affects Month 2–3 delivery.
  • Payment scope: decide whether release includes paid sessions and select a gateway/sandbox early. Real payment authorization must be verified server-side. Sales and transaction acceptance depend on this decision.
  • Voucher policies: the scaffold supports single-use full-bypass vouchers. Discount and reusable vouchers need explicit usage limits, discount rules and retry/concurrency behavior before Month 4 implementation.
  • Privacy: private galleries and viewer access need booth/tenant authorization. Public galleries need an explicit publication policy and agreed retention rules.
  • Traffic routing: with the selected serverless architecture, managed edge routing may satisfy the load-balancer item. Build a dedicated load balancer only if the chosen deployment requires it.
  • Testing throughout: cover duplicate requests, voucher reuse, failed/stalled uploads, connectivity loss, expired links, camera/printer failures and authorization boundaries—not only happy paths.
  • Cloud pause: this plan authorizes no deployment or billable test by itself. Resume paused infrastructure and live capacity tests only after an explicit request with agreed staging targets and limits.
  • Release acceptance: Month 6 timing depends on pilot results, security checks and operational readiness. Capacity targets remain unverified until measured on the real deployment.
